1. Старт проекта

Для NeoForge 1.21.1 используется Java 21. Официальный MDK можно создать через шаблон NeoGradle/ModDevGradle; после импорта Gradle IDE получает исходники Minecraft и NeoForge, что особенно важно для поиска реальных сигнатур API.

Правило: документация объясняет API, но исходники Minecraft/NeoForge остаются главным источником истины, когда сигнатура или поведение неочевидны.
./gradlew runClient
./gradlew runServer
./gradlew build

Сервер рекомендуется проверять отдельно: мод может работать в integrated server и при этом содержать ошибку, проявляющуюся на dedicated server.

2.2. Пошаговые цепочки: что делать по порядку

Если не знаете, с чего начать объект, идите по цепочке сверху вниз. На каждом шаге сначала добейтесь минимально рабочего результата, а затем переходите к следующему.

🧱 Item

  1. Создайте item/RubyItem.java, только если нужно собственное поведение.
  2. Зарегистрируйте имя в registry/ModItems.java.
  3. Напишите use(...), hurtEnemy(...) или другой нужный метод.
  4. Добавьте assets/modid/models/item/ruby.json и текстуру.
  5. Добавьте перевод в assets/modid/lang/.
  6. Запустите клиент и проверьте registry → модель → текстуру → поведение.

🧱 Block

  1. Создайте блок в block/, если нужна своя логика.
  2. Зарегистрируйте Block в registry/ModBlocks.java.
  3. Зарегистрируйте BlockItem в registry/ModItems.java.
  4. Для состояния используйте BlockState; для данных — переходите к BlockEntity.
  5. Добавьте blockstate/model/texture и перевод.
  6. Проверьте размещение, ломание, модель и drops.

⚙️ BlockEntity / машина

  1. Создайте block/entity/MachineBlockEntity.java.
  2. Зарегистрируйте BlockEntityType в registry/ModBlockEntities.java.
  3. Свяжите его с Block через newBlockEntity(...).
  4. Напишите tick(...) для серверной обработки.
  5. Добавьте сохранение данных и capability IItemHandler, если нужен инвентарь.
  6. Если нужен GUI: создайте Menu → зарегистрируйте Menu → создайте Screen → зарегистрируйте Screen.

👾 Entity / моб

  1. Создайте entity/... класс сущности.
  2. Зарегистрируйте EntityType в registry/ModEntities.java.
  3. Для моба добавьте attributes, AI и при необходимости spawn rules.
  4. Напишите tick() или другие методы только для собственной логики.
  5. В client/ создайте/зарегистрируйте renderer и model.
  6. Проверьте через /summon modid:name, затем отдельно проверяйте AI и внешний вид.

🖥️ GUI

  1. Определите, какие данные нужны серверу.
  2. Создайте Menu и добавьте слоты/data slots.
  3. Зарегистрируйте Menu в registry/ModMenus.java.
  4. Создайте Screen и напишите renderBg(...) / обработчики ввода.
  5. Зарегистрируйте Screen в клиентском событии.
  6. Для сложных действий добавьте network payload и проверку на сервере.

✨ Particle

  1. Зарегистрируйте ParticleType.
  2. Добавьте описание/ресурсы частицы.
  3. В client-коде зарегистрируйте provider.
  4. Создайте собственный Particle-класс только если sprite particle недостаточно.
  5. Вызовите частицу из серверной/клиентской логики в зависимости от задачи.
  6. Проверьте atlas, texture и provider, если частица невидима.

📡 Network payload

  1. Создайте network/payload/MyPayload.java.
  2. Опишите поля и StreamCodec.
  3. Зарегистрируйте payload в network/ModNetworking.java.
  4. Напишите handler как отдельный метод.
  5. На сервере валидируйте игрока, позицию, расстояние и входные данные.
  6. Проверяйте отдельно client → server и server → client.

📌 Event

  1. Выберите нужный event и правильную event bus.
  2. Создайте event/ModEvents.java.
  3. Напишите метод с @SubscribeEvent.
  4. Зарегистрируйте класс/метод там, где этого требует выбранный bus.
  5. Внутри метода отделите client/server логику.
  6. Если событие не срабатывает, первым делом проверьте bus и регистрацию.
Универсальная схема: 1. Файл класса → 2. Регистрация → 3. Собственный метод → 4. Связи с другими системами → 5. JSON/текстуры → 6. Тест в клиенте и dedicated server. Не каждый объект требует всех шести шагов.

public class MachineBlockEntity extends BlockEntity {

Событие

Как читать каркас: конструктор получает состояние/зависимости, переопределённый метод является точкой поведения, а регистрация связывает класс с Minecraft. Сначала добейтесь минимального рабочего класса, затем добавляйте sync, сохранение, capability и client rendering по необходимости.

3. Регистрация

📍 Где регистрировать: обычно registry/ModItems.java, ModBlocks.java, ModEntities.java и т. п. Здесь объект получает имя вроде ruby; сам класс поведения можно хранить в другом файле.

Регистрация делает объект известным игре. Для большинства объектов используйте DeferredRegister; для предметов и некоторых специализированных реестров есть удобные helpers.

public final class ModItems {
    public static final DeferredRegister.Items ITEMS =
        DeferredRegister.createItems(ExampleMod.MOD_ID);

    public static final DeferredItem RUBY = ITEMS.registerSimpleItem(
        "ruby", new Item.Properties()
    );

    public static void register(IEventBus modBus) {
        ITEMS.register(modBus);
    }
}

Конкретные helper-методы могут различаться между минорными 1.21.x; если IDE показывает другую сигнатуру, доверяйте текущему API вашего MDK.

4. Предметы

📍 Где создавать метод: если предмету нужно своё поведение, создайте отдельный класс вроде MagicWand.java. Переопределяемый use(...) — метод, который Minecraft вызывает при использовании предмета.

Базовый Item

public static final DeferredItem RUBY = ITEMS.registerItem(
    "ruby",
    Item::new,
    new Item.Properties().stacksTo(64)
);

Собственное поведение

public class MagicWand extends Item {
    public MagicWand(Properties properties) { super(properties); }

    @Override
    public InteractionResult use(Level level, Player player, InteractionHand hand) {
        if (!level.isClientSide) {
            player.sendSystemMessage(Component.literal("Волшебная палочка!"));
        }
        return InteractionResult.SUCCESS;
    }
}

Помните о разделении client/server: изменение мира обычно должно происходить на серверной стороне, а визуальный эффект — на клиентской.

5. Блоки

📍 Где создавать: регистрация блока — registry/ModBlocks.java; BlockItem — обычно в registry/ModItems.java; собственная логика блока — отдельный класс в block/. Если нужен инвентарь/таймер/энергия, переходите к BlockEntity.
public static final DeferredRegister.Blocks BLOCKS =
    DeferredRegister.createBlocks(ExampleMod.MOD_ID);

public static final DeferredBlock RUBY_BLOCK = BLOCKS.registerBlock(
    "ruby_block",
    Block::new,
    BlockBehaviour.Properties.of().strength(3.0f).requiresCorrectToolForDrops()
);

public static void register(IEventBus bus) {
    BLOCKS.register(bus);
}

Block + BlockItem

public static final DeferredItem RUBY_BLOCK_ITEM = ITEMS.registerSimpleBlockItem(
    "ruby_block", RUBY_BLOCK
);

Block states предназначены для конечного набора вариантов: facing, powered, waterlogged и т. п. Для больших/динамических данных используйте BlockEntity.

6. BlockEntity

📍 Где создавать: класс, например block/entity/MachineBlockEntity.java; его тип регистрируется отдельно, например в registry/ModBlockEntities.java. Метод tick(...) — место для периодической серверной логики.

BlockEntity хранит данные, которые не стоит кодировать в BlockState: инвентарь, энергию, таймеры, сложное состояние. Нужны отдельные BlockEntity и зарегистрированный BlockEntityType.

public class MachineBlockEntity extends BlockEntity {
    private int progress;

    public MachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MACHINE.get(), pos, state);
    }

    public static void tick(Level level, BlockPos pos, BlockState state,
                            MachineBlockEntity be) {
        if (level.isClientSide) return;
        be.progress++;
        be.setChanged();
    }
}
Если данные должны переживать сохранение мира — сериализируйте их через подходящий data/storage механизм. Для инвентарей в NeoForge 1.21.1 предпочтительна capability-модель IItemHandler, а не старые Container-паттерны.

7. Сущности

📍 Где создавать: entity/RubyProjectile.java — игровая логика; registry/ModEntities.java — EntityType; client/ — renderer/model. Не смешивайте client-only renderer с common-классом сущности.

Типичная сущность состоит из Entity-класса, зарегистрированного EntityType и клиентского EntityRenderer. Для мобов добавляются AI/attributes/spawn rules; для projectile — логика движения и столкновений.

public class RubyProjectile extends Entity {
    public RubyProjectile(EntityType type, Level level) {
        super(type, level);
    }

    @Override protected void defineSynchedData(SynchedEntityData.Builder b) {}
    @Override protected void readAdditionalSaveData(CompoundTag tag) {}
    @Override protected void addAdditionalSaveData(CompoundTag tag) {}

    @Override public void tick() {
        super.tick();
        if (!level().isClientSide) {
            // server-side movement / collision / effects
        }
    }
}

Для синхронизации используйте SynchedEntityData, spawn data или собственные network payloads в зависимости от типа данных.

8. Частицы

У частиц есть тип, клиентский provider и визуальная реализация. Простые sprite particles можно описать ресурсом; более сложные могут иметь собственный ParticleOptions, MapCodec и StreamCodec.

public static final DeferredRegister> PARTICLES =
    DeferredRegister.create(Registries.PARTICLE_TYPE, MOD_ID);

public static final Supplier SPARK =
    PARTICLES.register("spark", () -> new SimpleParticleType(false));

На клиенте регистрируется provider, который создаёт экземпляр particle. Для анимаций часто достаточно atlas/sprite sheet, а не собственного OpenGL-кода.

9. Меню и GUI

📍 Где создавать: MachineMenu.java — слоты и серверное состояние; MachineScreen.java — клиентская отрисовка; ModMenus.java — регистрация меню. Методы renderBg и обработчики ввода принадлежат Screen.

В NeoForge/vanilla GUI обычно разделяется на серверный AbstractContainerMenu и клиентский AbstractContainerScreen. Menu отвечает за слоты и синхронизацию данных; Screen — за отрисовку и ввод.

Для инвентарей используйте SlotItemHandler с capability. Числовые значения можно синхронизировать через DataSlot, а сложные данные — packet/networking.

9.1. Мини-пример: машина с GUI

Ниже цельный учебный скелет: блок открывает меню, BlockEntity хранит два слота и прогресс, Menu связывает инвентарь с GUI, а Screen рисует клиентскую часть. Это база для печи, дробилки, генератора и других машин.

1) Блок и открытие меню

public class MachineBlock extends BaseEntityBlock {
    public MachineBlock(Properties properties) {
        super(properties);
    }

    public static MapCodec codec() {
        return simpleCodec(MachineBlock::new);
    }

    @Override protected MapCodec codec() {
        return codec();
    }

    @Override public BlockEntity newBlockEntity(BlockPos pos, BlockState state) {
        return new MachineBlockEntity(pos, state);
    }

    @Override public InteractionResult useWithoutItem(BlockState state, Level level,
            BlockPos pos, Player player, BlockHitResult hit) {
        if (!level.isClientSide && player instanceof ServerPlayer serverPlayer
                && level.getBlockEntity(pos) instanceof MachineBlockEntity be) {
            NetworkHooks.openScreen(serverPlayer, be, pos);
        }
        return InteractionResult.SUCCESS;
    }
}

В конкретном MDK проверьте сигнатуру открытия меню и импорты: версии NeoForge могут менять детали API.

2) BlockEntity: инвентарь и обработка

public class MachineBlockEntity extends BlockEntity implements MenuProvider {
    private final ItemStackHandler inventory = new ItemStackHandler(2) {
        @Override protected void onContentsChanged(int slot) {
            setChanged();
        }
    };
    private int progress;

    public MachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MACHINE.get(), pos, state);
    }

    public static void tick(Level level, BlockPos pos, BlockState state,
                            MachineBlockEntity be) {
        if (level.isClientSide) return;
        if (!be.inventory.getStackInSlot(0).isEmpty()) {
            be.progress++;
            if (be.progress >= 100) {
                be.progress = 0;
                ItemStack input = be.inventory.extractItem(0, 1, false);
                be.inventory.insertItem(1,
                        new ItemStack(ModItems.RUBY.get(), input.isEmpty() ? 0 : 1), false);
            }
            be.setChanged();
        }
    }

    @Override public Component getDisplayName() {
        return Component.literal("Machine");
    }

    @Override public AbstractContainerMenu createMenu(int id, Inventory inv, Player player) {
        return new MachineMenu(id, inv, this);
    }

    public ItemStackHandler getInventory() { return inventory; }
    public int getProgress() { return progress; }
}

3) Menu: слоты машины + игрока

public class MachineMenu extends AbstractContainerMenu {
    private final MachineBlockEntity machine;

    public MachineMenu(int id, Inventory inv, MachineBlockEntity machine) {
        super(ModMenus.MACHINE.get(), id);
        this.machine = machine;

        addSlot(new SlotItemHandler(machine.getInventory(), 0, 56, 35));
        addSlot(new SlotItemHandler(machine.getInventory(), 1, 116, 35));

        for (int row = 0; row < 3; row++)
            for (int col = 0; col < 9; col++)
                addSlot(new Slot(inv, col + row * 9 + 9,
                        8 + col * 18, 84 + row * 18));
        for (int col = 0; col < 9; col++)
            addSlot(new Slot(inv, col, 8 + col * 18, 142));
    }

    @Override public boolean stillValid(Player player) {
        return stillValid(ContainerLevelAccess.create(
                machine.getLevel(), machine.getBlockPos()), player,
                ModBlocks.MACHINE.get());
    }

    @Override public ItemStack quickMoveStack(Player player, int index) {
        return ItemStack.EMPTY; // учебный пример: shift-click добавляется отдельно
    }
}

9.2. Мини-пример: простой моб

Для обычного наземного моба удобно наследоваться от PathfinderMob. Серверная сущность содержит AI и состояние, а клиентская часть отвечает за модель и renderer.

1) Entity-класс

public class RubyCreature extends PathfinderMob {
    protected RubyCreature(EntityType type, Level level) {
        super(type, level);
    }

    @Override protected void registerGoals() {
        goalSelector.addGoal(0, new FloatGoal(this));
        goalSelector.addGoal(2, new RandomStrollGoal(this, 1.0));
        goalSelector.addGoal(3, new LookAtPlayerGoal(this, Player.class, 8.0f));
        goalSelector.addGoal(4, new RandomLookAroundGoal(this));
    }
}

2) EntityType и атрибуты

public static final DeferredRegister> ENTITIES =
    DeferredRegister.create(Registries.ENTITY_TYPE, MOD_ID);

public static final Supplier> RUBY_CREATURE =
    ENTITIES.register("ruby_creature", () ->
        EntityType.Builder.of(RubyCreature::new, MobCategory.CREATURE)
            .sized(0.8f, 1.2f)
            .build(ResourceLocation.fromNamespaceAndPath(MOD_ID, "ruby_creature").toString()));

@SubscribeEvent
public static void registerAttributes(EntityAttributeCreationEvent event) {
    event.put(RUBY_CREATURE.get(),
        RubyCreature.createMobAttributes()
            .add(Attributes.MAX_HEALTH, 20.0)
            .add(Attributes.MOVEMENT_SPEED, 0.25)
            .add(Attributes.ATTACK_DAMAGE, 3.0)
            .build());
}

3) Клиентский renderer

@SubscribeEvent
public static void registerEntityRenderers(EntityRenderersEvent.RegisterRenderers event) {
    event.registerEntityRenderer(ModEntities.RUBY_CREATURE.get(),
        MobRenderer::new); // замените на renderer/model из вашего MDK
}
Важно: последний фрагмент — схема регистрации, а не готовая модель. Для красивого моба нужен конкретный ModelLayerLocation, модель/слои и renderer с текстурой; эти client API особенно чувствительны к версии.

После регистрации проверьте spawn rules, яйцо призыва или команду /summon examplemod:ruby_creature. Если моб существует, но невидим, сначала проверяйте client renderer/model/texture, а не AI.

Клиентская часть включает renderers, screens, particle providers, key mappings и визуальные эффекты. Архитектурно держите client-only классы в отдельном пакете и регистрируйте их только в клиентском lifecycle/event.

Model Layers

Entity Renderer

// src/main/java/com/example/mod/client/renderer/ExampleEntityRenderer.java
public record ExampleEntityRenderer(
    EntityType<? extends Entity>
) implements EntityRenderer {
    private final ModelLayerLocation layerLocation;

    public ExampleEntityRenderer(EntityType<? extends Entity> type) {
        this.layerLocation = new ExampleModelLayerLocation("example_mod", "entity");
    }

    @Override
    protected void render(
        Entity entity,
        float delta,
        MatrixStack matrixStack,
        PosePose pose,
        ParticleRenderer particleRenderer,
        Camera camera,
        int packedLight,
        int packedOverlay
    ) {
        // Отрисовка модели
        PoseStack poseStack = new PoseStack();
        poseStack.last().pose()
            .translate(entity.getX(), entity.getY(), entity.getZ());
        
        Matrix4f matrix = matrixStack.perspective(
            30.0f, (double) width / height,
            0.1, 1e8
        );
        matrixStack.multiply(matrix);
        poseStack.add(poseStack);
        
        ModelRenderer modelRenderer = new ModelRenderer(
            new ModelLayer(entity, layerLocation),
            new ModelBaker() // или ModelLoader
        );
        
        modelRenderer.render(particleRenderer, matrixStack, packedLight, packedOverlay);
    }
}

10. События и «процедуры»

📍 Где создавать метод: например, event/ModEvents.java. Метод с @SubscribeEvent создаёте вы, а NeoForge вызывает его при наступлении события. Для обычной процедуры без события метод можно написать в нужном gameplay-классе и вызвать напрямую.

Если под «процедурами» имеются в виду MCreator-подобные процедуры, в чистом NeoForge отдельной системы с таким названием нет. Аналог — обычные Java-методы, вызываемые из событий, tick-методов, callbacks, команд и network handlers.

Два event bus: mod event bus используется для lifecycle/регистрационных событий; NeoForge game event bus — для игровых событий. Неправильная шина часто является причиной «метод не вызывается».

11. Networking

📍 Где создавать: payload — например network/payload/OpenMachinePayload.java; регистрация — network/ModNetworking.java; обработчик — отдельный метод, который получает payload. Так структура пакета не смешивается с игровой логикой.

В 1.21.1 современный подход — custom payloads и RegisterPayloadHandlersEvent. Сначала определяют payload, его codec/stream codec, затем регистрируют обработчик.

public record OpenMachinePayload(BlockPos pos)
        implements CustomPacketPayload {
    public static final Type TYPE =
        new Type<>(ResourceLocation.fromNamespaceAndPath(MOD_ID, "open_machine"));

    public static final StreamCodec STREAM_CODEC =
        StreamCodec.composite(
            BlockPos.STREAM_CODEC, OpenMachinePayload::pos,
            OpenMachinePayload::new
        );

    @Override public Type type() { return TYPE; }
}

Никогда не доверяйте данным от клиента: packet handler должен проверять игрока, позицию, расстояние, состояние мира и права.

14. Команды

Команды регистрируются через событие команд. Brigadier отвечает за parsing, suggestions, permissions и execution.

@SubscribeEvent
public static void registerCommands(RegisterCommandsEvent event) {
    event.getDispatcher().register(
        Commands.literal("example")
            .requires(src -> src.hasPermission(2))
            .then(Commands.literal("hello")
                .executes(ctx -> {
                    ctx.getSource().sendSuccess(
                        () -> Component.literal("Hello!"), true);
                    return 1;
                }))
    );
}

21. Модификации vanilla через Mixin

Важно: Mixin — это инструмент для расширения классов, а не замены их поведения. Неправильное использование может привести к конфликтам и непредсказуемым результатам.

Mixin позволяет добавлять методы в существующие классы Minecraft/NeoForge без наследования. Это полезно для расширения функциональности с минимальным вмешательством в оригинальный код.

Как использовать Mixin

  1. Создайте файл src/main/java/com/example/mod/mixin/ExampleMixin.java
  2. Укажите класс-мишень и метод для расширения
  3. Реализуйте методы, которые будут вызываться в точке расширения
  4. Регистрируйте Mixin через MixinTransformerConfig

Пример Mixin

@Mixin(Block.class)
@RequiredArgsConstructor
public class ExampleBlockMixin {
    private final Block block;

    @Inject(at = @At("TAIL"), remap = false)
    public void onBlockPlaced(BlockPlacementEvent event) {
        // Расширяем логику при размещении блока
        if (event.getState().hasProperty("custom", Boolean.class)) {
            // кастомная логика
        }
    }
}

Регистрация Mixin

Mixin трансформаторы должны быть зарегистрированы через MixinTransformerConfig.

# src/main/resources/META-INF/neoforge.mixins.json
{
    "transformers": [
        {
            "remapInput": true,
            "config": "example.mixins.json"
        }
    ]
}

# src/main/resources/example.mixins.json
[
    {
        "from": ["net.minecraft.block.Block"],
        "method": "placeItemInWorld",
        "at": [
            {
                "type": "INVOKE",
                "target": "com.example.mod.mixin.ExampleBlockMixin::onBlockPlaced"
            }
        ]
    }
]

Когда использовать Mixin

Использовать Mixin:
  • Расширение существующего API без наследования
  • Минимальное вмешательство в оригинальный код
  • Адаптация к изменениям в Minecraft/NeoForge
Не использовать Mixin:
  • Замена основного поведения (лучше наследование)
  • Сложная логика с состоянием (лучше собственный класс)
  • Когда нужно полное переопределение метода

Пример: расширение BlockItem

@Mixin(BlockItem.class)
@RequiredArgsConstructor
public class ExampleBlockItemMixin {
    private final BlockItem blockItem;

    @Inject(at = "@RETURN", remap = false)
    public void onRightClick(BlockHitResult hit) {
        // Расширяем логику при правом клике
        if (hit.getBlockState().hasProperty("custom_action")) {
            // кастомное действие
        }
    }
}

Безопасность Mixin

Правила безопасности:
  • Используйте @At("TAIL") для расширения после основного кода
  • Избегайте конфликтов с существующими @Inject методами
  • Проверяйте версии Minecraft/NeoForge при регистрации
  • Не используйте Mixin для критических систем (спавн, AI)

Для получения актуальной информации о Mixin API и конфигурации смотрите официальную документацию NeoForge.

21.2. Data Components & Component API

Data Components — это современный подход к хранению данных в Minecraft, который заменяет/дополняет Attachments для ItemStack и других holder-объектов.

Преимущества:
  • Типизированные данные через Component
  • Удобная сериализация через JSON/CompoundTag
  • Более гибкая работа с данными

Основные типы Component

// Для ItemStack
ItemStack stack = new ItemStack(ModItems.RUBY.get());
Component component = Component.empty();
stack.set(DataComponents.MANA, 100); // установка значения
int mana = stack.get(DataComponents.MANA); // получение значения

// Для Entity
Entity entity = player;
entity.setData(ModAttachments.MANA, 100);
int mana = entity.getData(ModAttachments.MANA);

// Для BlockEntity
BlockEntity be = level.getBlockEntity(pos);
be.setData(ModAttachments.PROGRESS, 50);

Создание кастомных Component

// src/main/java/com/example/mod/data/ManaComponent.java
public record ManaComponent(int value) implements DataComponent {
    public static final AttachmentType<Integer> TYPE =
        AttachmentType.builder(() -> 0)
            .serialize(Codec.INT)
            .build();
}

// Использование
ItemStack stack = new ItemStack(ModItems.RUBY.get());
stack.set(DataComponents.MANA, 100);
Component component = Component.empty()
    .append(DataComponents.MANA, 100);

Serialization & Deserialization

Data Components автоматически сериализуются в JSON/CompoundTag при сохранении.

// Пример сохранения и загрузки
public class MachineBlockEntity extends BlockEntity {
    private int progress;

    public MachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MACHINE.get(), pos, state);
    }

    @Override protected void readAdditionalSaveData(CompoundTag tag) {
        super.readAdditionalSaveData(tag);
        progress = tag.getInt("progress");
    }

    @Override protected void addAdditionalSaveData(CompoundTag tag) {
        super.addAdditionalSaveData(tag);
        tag.putInt("progress", progress);
    }
}

Component vs String

Использовать Component:
  • Когда нужны типы данных (int, boolean, List<String>)
  • Для сериализации в JSON/CompoundTag
  • При работе с Data Attachments
Использовать String:
  • Для простых флагов (enabled, locked)
  • Когда данные не требуют типизации
  • В конфигурационных файлах

Для ItemStack в NeoForge 1.21.1 предпочтительнее использовать Data Components через DataComponents.MANA, чем кастомные Attachments.

public class ModDataGenerators {
    public static void gather(GatherDataEvent event) {
        PackOutput output = event.getGenerator().getPackOutput();
        ExistingFileHelper helper = event.getExistingFileHelper();

        // Генерация биомов
        event.addProvider(true, new ModBiomeProvider(output));
        
        // Генерация структур
        event.addProvider(true, new ModStructureProvider(output));
        
        // Генерация декораций
        event.addProvider(true, new ModDecorationProvider(output));
    }
}
