1. Старт проекта

Для NeoForge 1.21.1 используется Java 21. Официальный MDK можно создать через шаблон NeoGradle/ModDevGradle; после импорта Gradle IDE получает исходники Minecraft и NeoForge, что особенно важно для поиска реальных сигнатур API.

Правило: документация объясняет API, но исходники Minecraft/NeoForge остаются главным источником истины, когда сигнатура или поведение неочевидны.
./gradlew runClient
./gradlew runServer
./gradlew build

Сервер рекомендуется проверять отдельно: мод может работать в integrated server и при этом содержать ошибку, проявляющуюся на dedicated server.

2.2. Пошаговые цепочки: что делать по порядку

Если не знаете, с чего начать объект, идите по цепочке сверху вниз. На каждом шаге сначала добейтесь минимально рабочего результата, а затем переходите к следующему.

🧱 Item

  1. Создайте item/RubyItem.java, только если нужно собственное поведение.
  2. Зарегистрируйте имя в registry/ModItems.java.
  3. Напишите use(...), hurtEnemy(...) или другой нужный метод.
  4. Добавьте assets/modid/models/item/ruby.json и текстуру.
  5. Добавьте перевод в assets/modid/lang/.
  6. Запустите клиент и проверьте registry → модель → текстуру → поведение.

🧱 Block

  1. Создайте блок в block/, если нужна своя логика.
  2. Зарегистрируйте Block в registry/ModBlocks.java.
  3. Зарегистрируйте BlockItem в registry/ModItems.java.
  4. Для состояния используйте BlockState; для данных — переходите к BlockEntity.
  5. Добавьте blockstate/model/texture и перевод.
  6. Проверьте размещение, ломание, модель и drops.

⚙️ BlockEntity / машина

  1. Создайте block/entity/MachineBlockEntity.java.
  2. Зарегистрируйте BlockEntityType в registry/ModBlockEntities.java.
  3. Свяжите его с Block через newBlockEntity(...).
  4. Напишите tick(...) для серверной обработки.
  5. Добавьте сохранение данных и capability IItemHandler, если нужен инвентарь.
  6. Если нужен GUI: создайте Menu → зарегистрируйте Menu → создайте Screen → зарегистрируйте Screen.

👾 Entity / моб

  1. Создайте entity/... класс сущности.
  2. Зарегистрируйте EntityType в registry/ModEntities.java.
  3. Для моба добавьте attributes, AI и при необходимости spawn rules.
  4. Напишите tick() или другие методы только для собственной логики.
  5. В client/ создайте/зарегистрируйте renderer и model.
  6. Проверьте через /summon modid:name, затем отдельно проверяйте AI и внешний вид.

🖥️ GUI

  1. Определите, какие данные нужны серверу.
  2. Создайте Menu и добавьте слоты/data slots.
  3. Зарегистрируйте Menu в registry/ModMenus.java.
  4. Создайте Screen и напишите renderBg(...) / обработчики ввода.
  5. Зарегистрируйте Screen в клиентском событии.
  6. Для сложных действий добавьте network payload и проверку на сервере.

✨ Particle

  1. Зарегистрируйте ParticleType.
  2. Добавьте описание/ресурсы частицы.
  3. В client-коде зарегистрируйте provider.
  4. Создайте собственный Particle-класс только если sprite particle недостаточно.
  5. Вызовите частицу из серверной/клиентской логики в зависимости от задачи.
  6. Проверьте atlas, texture и provider, если частица невидима.

📡 Network payload

  1. Создайте network/payload/MyPayload.java.
  2. Опишите поля и StreamCodec.
  3. Зарегистрируйте payload в network/ModNetworking.java.
  4. Напишите handler как отдельный метод.
  5. На сервере валидируйте игрока, позицию, расстояние и входные данные.
  6. Проверяйте отдельно client → server и server → client.

📌 Event

  1. Выберите нужный event и правильную event bus.
  2. Создайте event/ModEvents.java.
  3. Напишите метод с @SubscribeEvent.
  4. Зарегистрируйте класс/метод там, где этого требует выбранный bus.
  5. Внутри метода отделите client/server логику.
  6. Если событие не срабатывает, первым делом проверьте bus и регистрацию.
Универсальная схема: 1. Файл класса → 2. Регистрация → 3. Собственный метод → 4. Связи с другими системами → 5. JSON/текстуры → 6. Тест в клиенте и dedicated server. Не каждый объект требует всех шести шагов.

2.3. Минимальные скелеты классов

Ниже не «магические» готовые системы, а короткие каркасы, от которых удобно начинать реальный класс. Имена пакетов и регистрации показаны намеренно явно.

Обычный Item

public class RubyItem extends Item {
    public RubyItem(Properties properties) {
        super(properties);
    }

    @Override
    public InteractionResult use(Level level, Player player,
                                 InteractionHand hand) {
        // gameplay logic
        return InteractionResult.SUCCESS;
    }
}

BlockEntity

public class MachineBlockEntity extends BlockEntity {
    public MachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MACHINE.get(), pos, state);
    }

    public static void tick(Level level, BlockPos pos,
                            BlockState state, MachineBlockEntity be) {
        if (level.isClientSide) return;
        // server tick
    }
}

Событие

public final class ModEvents {
    @SubscribeEvent
    public static void onJoin(PlayerEvent.PlayerLoggedInEvent event) {
        Player player = event.getEntity();
        // reaction to event
    }
}

Screen

public class MachineScreen
        extends AbstractContainerScreen<MachineMenu> {
    public MachineScreen(MachineMenu menu, Inventory inv,
                         Component title) {
        super(menu, inv, title);
    }

    @Override
    protected void renderBg(GuiGraphics g, float partialTick,
                            int mouseX, int mouseY) {
        // draw background
    }
}
Как читать каркас: конструктор получает состояние/зависимости, переопределённый метод является точкой поведения, а регистрация связывает класс с Minecraft. Сначала добейтесь минимального рабочего класса, затем добавляйте sync, сохранение, capability и client rendering по необходимости.

3. Регистрация

📍 Где регистрировать: обычно registry/ModItems.java, ModBlocks.java, ModEntities.java и т. п. Здесь объект получает имя вроде ruby; сам класс поведения можно хранить в другом файле.

Регистрация делает объект известным игре. Для большинства объектов используйте DeferredRegister; для предметов и некоторых специализированных реестров есть удобные helpers.

public final class ModItems {
    public static final DeferredRegister.Items ITEMS =
        DeferredRegister.createItems(ExampleMod.MOD_ID);

    public static final DeferredItem RUBY = ITEMS.registerSimpleItem(
        "ruby", new Item.Properties()
    );

    public static void register(IEventBus modBus) {
        ITEMS.register(modBus);
    }
}

Конкретные helper-методы могут различаться между минорными 1.21.x; если IDE показывает другую сигнатуру, доверяйте текущему API вашего MDK.

4. Предметы

📍 Где создавать метод: если предмету нужно своё поведение, создайте отдельный класс вроде MagicWand.java. Переопределяемый use(...) — метод, который Minecraft вызывает при использовании предмета.

Базовый Item

public static final DeferredItem RUBY = ITEMS.registerItem(
    "ruby",
    Item::new,
    new Item.Properties().stacksTo(64)
);

Собственное поведение

public class MagicWand extends Item {
    public MagicWand(Properties properties) { super(properties); }

    @Override
    public InteractionResult use(Level level, Player player, InteractionHand hand) {
        if (!level.isClientSide) {
            player.sendSystemMessage(Component.literal("Волшебная палочка!"));
        }
        return InteractionResult.SUCCESS;
    }
}

Помните о разделении client/server: изменение мира обычно должно происходить на серверной стороне, а визуальный эффект — на клиентской.

4.1. Предметы: поведение и ItemStack

У Item есть несколько точек расширения. Выбирайте их по действию: use для ПКМ, useOn для взаимодействия с блоком, finishUsingItem для завершения длительного использования, releaseUsing для отпускания кнопки, hurtEnemy для атак и inventoryTick для периодической логики.

Item описывает тип предмета, а ItemStack — конкретный экземпляр с количеством, durability, enchantments и Data Components. Изменяемое состояние конкретного предмета обычно должно жить в ItemStack, а не в полях singleton-объекта Item.

ItemStack stack = player.getItemInHand(hand);
stack.set(DataComponents.CUSTOM_NAME, Component.literal("Ruby Wand"));
stack.hurtAndBreak(1, player, EquipmentSlot.MAINHAND);

Инструменты и Item Abilities

В NeoForge 1.21.1 современные инструменты могут использовать Tool Data Component, правила добычи, атрибуты и ItemAbility. Это позволяет делать multitool-подобные предметы без обязательного наследования от одного vanilla tool-класса.

Практическое правило: сначала определите роль предмета, затем выбирайте комбинацию Item methods, components, attributes и abilities.

4.2. Зачарования

В 1.21.1 зачарования являются datapack registry objects. Собственное зачарование не следует представлять как просто статическое Java-значение: его данные загружаются как registry/datapack data, а ссылки работают через registry holders и vanilla helpers.

Особенно важны supported_items и primary_items: первое задаёт поддерживаемые предметы, второе — подмножество, подходящее для получения через стол зачарований.

{
  "description": {"translate": "enchantment.examplemod.power"},
  "supported_items": "#examplemod:enchantable/my_tools",
  "primary_items": "#examplemod:enchantable/my_tools"
}

Для собственных инструментов проверяйте соответствующие minecraft:enchantable/* tags. Зачарования ItemStack связаны с Data Components, поэтому не создавайте вторую параллельную систему хранения без необходимости.

Версионная оговорка: JSON и Java helpers для enchantments менялись внутри 1.21.x. Конкретные holder/codec вызовы перед copy-paste сверяйте с MDK 1.21.1.

5. Блоки

📍 Где создавать: регистрация блока — registry/ModBlocks.java; BlockItem — обычно в registry/ModItems.java; собственная логика блока — отдельный класс в block/. Если нужен инвентарь/таймер/энергия, переходите к BlockEntity.
public static final DeferredRegister.Blocks BLOCKS =
    DeferredRegister.createBlocks(ExampleMod.MOD_ID);

public static final DeferredBlock RUBY_BLOCK = BLOCKS.registerBlock(
    "ruby_block",
    Block::new,
    BlockBehaviour.Properties.of().strength(3.0f).requiresCorrectToolForDrops()
);

public static void register(IEventBus bus) {
    BLOCKS.register(bus);
}

Block + BlockItem

public static final DeferredItem RUBY_BLOCK_ITEM = ITEMS.registerSimpleBlockItem(
    "ruby_block", RUBY_BLOCK
);

Block states предназначены для конечного набора вариантов: facing, powered, waterlogged и т. п. Для больших/динамических данных используйте BlockEntity.

5.1. BlockState и взаимодействия

BlockState — конечный набор свойств блока: например facing, powered, waterlogged или вариант формы. Если данные произвольны, велики или требуют сохранения, это сигнал перейти к BlockEntity.

Свойства состояния

Свойство объявляется в классе блока, добавляется в state definition и меняется через state.setValue(...). Каждый набор значений является отдельным BlockState.

public static final BooleanProperty POWERED = BlockStateProperties.POWERED;

@Override
protected void createBlockStateDefinition(StateDefinition.Builder<Block, BlockState> builder) {
    builder.add(POWERED);
}

BlockState next = state.setValue(POWERED, true);

ПКМ по блоку

Для блока без предмета используйте современный interaction path useWithoutItem; BlockHitResult содержит информацию о месте попадания и стороне блока.

Когда BlockState, а когда BlockEntity

6. BlockEntity

📍 Где создавать: класс, например block/entity/MachineBlockEntity.java; его тип регистрируется отдельно, например в registry/ModBlockEntities.java. Метод tick(...) — место для периодической серверной логики.

BlockEntity хранит данные, которые не стоит кодировать в BlockState: инвентарь, энергию, таймеры, сложное состояние. Нужны отдельные BlockEntity и зарегистрированный BlockEntityType.

public class MachineBlockEntity extends BlockEntity {
    private int progress;

    public MachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MACHINE.get(), pos, state);
    }

    public static void tick(Level level, BlockPos pos, BlockState state,
                            MachineBlockEntity be) {
        if (level.isClientSide) return;
        be.progress++;
        be.setChanged();
    }
}
Если данные должны переживать сохранение мира — сериализуйте их через подходящий data/storage механизм. Для инвентарей в NeoForge 1.21.1 предпочтительна capability-модель IItemHandler, а не старые Container-паттерны.

7. Сущности

📍 Где создавать: entity/RubyProjectile.java — игровая логика; registry/ModEntities.java — EntityType; client/ — renderer/model. Не смешивайте client-only renderer с common-классом сущности.

Типичная сущность состоит из Entity-класса, зарегистрированного EntityType и клиентского EntityRenderer. Для мобов добавляются AI/attributes/spawn rules; для projectile — логика движения и столкновений.

public class RubyProjectile extends Entity {
    public RubyProjectile(EntityType type, Level level) {
        super(type, level);
    }

    @Override protected void defineSynchedData(SynchedEntityData.Builder b) {}
    @Override protected void readAdditionalSaveData(CompoundTag tag) {}
    @Override protected void addAdditionalSaveData(CompoundTag tag) {}

    @Override public void tick() {
        super.tick();
        if (!level().isClientSide) {
            // server-side movement / collision / effects
        }
    }
}

Для синхронизации используйте SynchedEntityData, spawn data или собственные network payloads в зависимости от типа данных.

7.1. AI, projectile и синхронизация

Обычный моб

Для мобов отдельно рассматривайте четыре слоя: EntityType, attributes, AI goals и spawn rules. Не стоит помещать всё в tick(): GoalSelector уже предоставляет систему приоритетов и жизненного цикла поведения.

GoalSelector

Обычно цели добавляются в registerGoals(). Низкий номер означает более высокий приоритет. Комбинируйте movement goals, target goals и look goals, а не создавайте один огромный метод AI.

@Override
protected void registerGoals() {
    goalSelector.addGoal(0, new FloatGoal(this));
    goalSelector.addGoal(2, new RandomStrollGoal(this, 1.0));
    goalSelector.addGoal(3, new LookAtPlayerGoal(this, Player.class, 8.0f));
}

Projectile

Projectile обычно имеет отдельную логику движения, столкновения и результата попадания. Renderer нужен только для клиентского представления. Урон и изменение мира должны выполняться на серверной стороне.

Синхронизация Entity

Для небольших значений, которые должны быть видны клиенту, используйте SynchedEntityData. Для данных, необходимых только при создании сущности, подходит spawn data. Для сложных или событийных обновлений используйте network payload.

Если моб есть, но не появляется

  1. Проверьте EntityType и attributes.
  2. Проверьте spawn placement и biome/category ограничения.
  3. Проверьте свет, высоту и условия спавна.
  4. Проверьте, что тестовый /summon работает.
  5. Только после этого отлаживайте естественный spawn.

8. Частицы

У частиц есть тип, клиентский provider и визуальная реализация. Простые sprite particles можно описать ресурсом; более сложные могут иметь собственный ParticleOptions, MapCodec и StreamCodec.

public static final DeferredRegister> PARTICLES =
    DeferredRegister.create(Registries.PARTICLE_TYPE, MOD_ID);

public static final Supplier SPARK =
    PARTICLES.register("spark", () -> new SimpleParticleType(false));

На клиенте регистрируется provider, который создаёт экземпляр particle. Для анимаций часто достаточно atlas/sprite sheet, а не собственного OpenGL-кода.

8.1. Звуки

Звуковая система состоит из зарегистрированного SoundEvent и ресурса sounds.json, который описывает реальные audio files. Игровой код должен ссылаться на зарегистрированный sound event, а не напрямую на файл.

Структура ресурсов

assets/examplemod/sounds/stalker_living.ogg
assets/examplemod/sounds.json
{
  "stalker_living": {
    "sounds": ["examplemod:stalker_living"]
  }
}

Если звук не воспроизводится, проверяйте namespace, путь без расширения в JSON, формат файла и регистрацию SoundEvent. Для positional sounds учитывайте, что источник звука находится в мире, а не только на экране клиента.

9. Меню и GUI

📍 Где создавать: MachineMenu.java — слоты и серверное состояние; MachineScreen.java — клиентская отрисовка; ModMenus.java — регистрация меню. Методы renderBg и обработчики ввода принадлежат Screen.

В NeoForge/vanilla GUI обычно разделяется на серверный AbstractContainerMenu и клиентский AbstractContainerScreen. Menu отвечает за слоты и синхронизацию данных; Screen — за отрисовку и ввод.

public class MachineMenu extends AbstractContainerMenu {

        super(ModMenus.MACHINE.get(), id);
        // addSlot(new SlotItemHandler(...));
        // addDataSlot(...);
    }

    @Override public boolean stillValid(Player player) {
        return true;
    }
}

public class MachineScreen extends AbstractContainerScreen {
    public MachineScreen(MachineMenu menu, Inventory inv, Component title) {
        super(menu, inv, title);
    }

    @Override protected void renderBg(GuiGraphics g, float partialTick,
                                     int mouseX, int mouseY) {
        // g.blit(...)
    }
}

Для инвентарей используйте SlotItemHandler с capability. Числовые значения можно синхронизировать через DataSlot, а сложные данные — packet/networking.

9.1. Screen: координаты, widgets и отрисовка

Screen работает в относительной системе координат: x увеличивается слева направо, y — сверху вниз. Масштаб зависит от GUI Scale, поэтому интерфейс нельзя привязывать к физическим пикселям окна.

Позиционирование относительно GUI

У AbstractContainerScreen поля leftPos и topPos обозначают верхний левый угол фонового изображения. От них удобно строить все координаты.

РасположениеФормула
Верхний левыйx=leftPos+margin, y=topPos+margin
Верхний правыйx=leftPos+imageWidth-elementWidth-margin
Нижний левыйy=topPos+imageHeight-elementHeight-margin
Нижний правыйx=leftPos+imageWidth-elementWidth-margin, y=topPos+imageHeight-elementHeight-margin
По центруx=leftPos+(imageWidth-elementWidth)/2, y=topPos+(imageHeight-elementHeight)/2
Центр текстаx=leftPos+(imageWidth-font.width(text))/2

Когда выполнять расчёты

Динамические координаты и создание widgets следует делать в init(), потому что Screen переинициализируется после изменения размера окна.

Widgets

addWidget — интерактивный, но не отрисовываемый; addRenderableOnly — только отрисовка; addRenderableWidget — интерактивный и отрисовываемый вариант. Для обычных кнопок и EditBox чаще всего нужен последний.

@Override
protected void init() {
    super.init();
    int w = 80, h = 20;
    int x = leftPos + (imageWidth - w) / 2;
    int y = topPos + imageHeight - h - 8;
    addRenderableWidget(Button.builder(
        Component.literal("Start"),
        button -> sendStartPayload()
    ).bounds(x, y, w, h).build());
}

Жизненный цикл

init() — построение интерфейса; tick() — client-side логика; render() — общий рендер; renderBg() — фон container screen; renderLabels() — подписи; onClose() — закрытие; removed() — окончательная очистка.

Слои

Обычно фон рисуется первым, затем labels/widgets, затем tooltips. Для texture используйте GuiGraphics#blit; для простых индикаторов — fill, hLine, vLine.

9.2. Menu: слоты и синхронизация

Menu — view над данными, а не само хранилище. Он связывает Screen с BlockEntity, inventory или другим data holder. MenuType регистрируется, а конкретные Menu создаются динамически.

Порядок слотов

Индексы критичны для quickMoveStack. Если сначала добавлены два слота машины, они занимают 0–1; затем инвентарь игрока и hotbar получают следующие индексы. Эти диапазоны должны совпадать с shift-click логикой.

// machine slots: 0..1
addSlot(new SlotItemHandler(machine.getInventory(), 0, 56, 35));
addSlot(new SlotItemHandler(machine.getInventory(), 1, 116, 35));

// player inventory: 2..28
// hotbar: 29..37

quickMoveStack

Shift-click вызывает quickMoveStack. Обычно используется moveItemStackTo для перемещения между диапазонами. Этот метод определяет реальные правила быстрых перемещений.

DataSlot

DataSlot подходит для небольших числовых значений GUI: progress, energy level, timer. Более сложные структуры лучше синхронизировать собственным payload.

Клиентский Menu

Клиент иногда создаёт Menu с dummy holder. Если Screen должен знать позицию BlockEntity или другие дополнительные данные, для открытия меню можно использовать IContainerFactory и передать их из сервера.

9.3. Мини-пример: машина с GUI

Ниже цельный учебный скелет: блок открывает меню, BlockEntity хранит два слота и прогресс, Menu связывает инвентарь с GUI, а Screen рисует клиентскую часть. Это база для печи, дробилки, генератора и других машин.

1) Блок и открытие меню

public class MachineBlock extends BaseEntityBlock {
    public MachineBlock(Properties properties) {
        super(properties);
    }

    public static MapCodec<MachineBlock> codec() {
        return simpleCodec(MachineBlock::new);
    }

    @Override protected MapCodec<? extends BaseEntityBlock> codec() {
        return codec();
    }

    @Override public BlockEntity newBlockEntity(BlockPos pos, BlockState state) {
        return new MachineBlockEntity(pos, state);
    }

    @Override public InteractionResult useWithoutItem(BlockState state, Level level,
            BlockPos pos, Player player, BlockHitResult hit) {
        if (!level.isClientSide && player instanceof ServerPlayer serverPlayer
                && level.getBlockEntity(pos) instanceof MachineBlockEntity be) {
            NetworkHooks.openScreen(serverPlayer, be, pos);
        }
        return InteractionResult.SUCCESS;
    }
}

В конкретном MDK проверьте сигнатуру открытия меню и импорты: версии NeoForge могут менять детали API.

2) BlockEntity: инвентарь и обработка

public class MachineBlockEntity extends BlockEntity implements MenuProvider {
    private final ItemStackHandler inventory = new ItemStackHandler(2) {
        @Override protected void onContentsChanged(int slot) {
            setChanged();
        }
    };
    private int progress;

    public MachineBlockEntity(BlockPos pos, BlockState state) {
        super(ModBlockEntities.MACHINE.get(), pos, state);
    }

    public static void tick(Level level, BlockPos pos, BlockState state,
                            MachineBlockEntity be) {
        if (level.isClientSide) return;
        if (!be.inventory.getStackInSlot(0).isEmpty()) {
            be.progress++;
            if (be.progress >= 100) {
                be.progress = 0;
                ItemStack input = be.inventory.extractItem(0, 1, false);
                be.inventory.insertItem(1,
                        new ItemStack(ModItems.RUBY.get(), input.isEmpty() ? 0 : 1), false);
            }
            be.setChanged();
        }
    }

    @Override public Component getDisplayName() {
        return Component.literal("Machine");
    }

    @Override public AbstractContainerMenu createMenu(int id, Inventory inv, Player player) {
        return new MachineMenu(id, inv, this);
    }

    public ItemStackHandler getInventory() { return inventory; }
    public int getProgress() { return progress; }
}

Для обычного наземного моба удобно наследоваться от PathfinderMob. Серверная сущность содержит AI и состояние, а клиентская часть отвечает за модель и renderer.

1) Entity-класс

public class RubyCreature extends PathfinderMob {

10. События и «процедуры»

📍 Где создавать метод: например, event/ModEvents.java. Метод с @SubscribeEvent создаёте вы, а NeoForge вызывает его при наступлении события. Для обычной процедуры без события метод можно написать в нужном gameplay-классе и вызвать напрямую.

Если под «процедурами» имеются в виду MCreator-подобные процедуры, в чистом NeoForge отдельной системы с таким названием нет. Аналог — обычные Java-методы, вызываемые из событий, tick-методов, callbacks, команд и network handlers.

Регистрация объектовMod Event Bus + DeferredRegister
Реакция на игровой моментGame Event Bus / @SubscribeEvent
Клиентская настройкаClient events / client mod bus
Периодическая логикаServerTickEvent / LevelTickEvent / BlockEntity ticker
Ввод игрокаKey Mapping + client input event
Изменение мираServer-side event или прямой API Minecraft
Связь client↔serverCustom Packet Payload
@SubscribeEvent
public static void onPlayerJoin(PlayerEvent.PlayerLoggedInEvent event) {
    Player player = event.getEntity();
    player.sendSystemMessage(Component.literal("Добро пожаловать!"));
}
Два event bus: mod event bus используется для lifecycle/регистрационных событий; NeoForge game event bus — для игровых событий. Неправильная шина часто является причиной «метод не вызывается».

11. Networking

📍 Где создавать: payload — например network/payload/OpenMachinePayload.java; регистрация — network/ModNetworking.java; обработчик — отдельный метод, который получает payload. Так структура пакета не смешивается с игровой логикой.

В 1.21.1 современный подход — custom payloads и RegisterPayloadHandlersEvent. Сначала определяют payload, его codec/stream codec, затем регистрируют обработчик.

public record OpenMachinePayload(BlockPos pos)
        implements CustomPacketPayload {
    public static final Type TYPE =
        new Type<>(ResourceLocation.fromNamespaceAndPath(MOD_ID, "open_machine"));

    public static final StreamCodec STREAM_CODEC =
        StreamCodec.composite(
            BlockPos.STREAM_CODEC, OpenMachinePayload::pos,
            OpenMachinePayload::new
        );

    @Override public Type type() { return TYPE; }
}

Никогда не доверяйте данным от клиента: packet handler должен проверять игрока, позицию, расстояние, состояние мира и права.

Networking ↗

11.1. Client → Server, Server → Client и безопасность

Разделяйте направления payload на уровне архитектуры. Client → Server сообщает намерение игрока; Server → Client сообщает результат или визуальное состояние. Сервер остаётся источником истины для изменения мира.

НаправлениеТипичный пример
Client → ServerКнопка GUI, клавиша, способность, ввод текста
Server → ClientПрогресс, UI-состояние, визуальный эффект
Оба направленияСинхронизация состояния, принадлежащего серверу

Проверки handler

  • Кто отправил payload?
  • Есть ли право на действие?
  • Достаточно ли близко игрок находится к объекту?
  • Существует ли объект и находится ли он в нужном состоянии?
  • Валидны ли числа, enum, позиции и идентификаторы?
  • Не даёт ли payload доступ к произвольной позиции или предмету?
// Схема проверки на сервере
if (!playerHasPermission) return;
if (!level.hasChunkAt(pos)) return;
if (player.distanceToSqr(pos.getX(), pos.getY(), pos.getZ()) > 64) return;
// только после проверок изменяем состояние
Главное правило: Screen сообщает намерение. Сервер решает, допустимо ли действие.

17.1. Enchantments, Data Maps и Data Load Conditions

Enchantments

18.1. Rendering

Рендеринг лучше отделять от игровой логики. Entity/BlockEntity знают, что происходит; renderer решает, как это выглядит на клиенте.

Типичные client-only части

  • EntityRenderer и модель сущности.
  • BlockEntityRenderer.
  • Screen и widgets.
  • Particle provider.
  • HUD и overlays.
  • Model layer registration.

Если объект невидим

  1. Проверьте registry ID.
  2. Проверьте регистрацию renderer на клиенте.
  3. Проверьте model layer/модель.
  4. Проверьте texture path в assets/modid/textures/....
  5. Убедитесь, что client-only класс не попал в common код.
  6. Посмотрите client log на missing texture/model.
Для Screen используется GuiGraphics; для Entity — renderer/model pipeline. Не смешивайте их координатные системы и жизненные циклы.

Screen → Button → payload → Server validation → state change → sync.

Снаряд

EntityType → projectile → movement/collision → damage/effect → renderer.

Состояние игрока

Attachment → serialization → server authority → client sync → UI/HUD.

Особый BlockState

Property → state definition → interaction/update → blockstate JSON → model variants. Если состояние не укладывается в конечный набор — BlockEntity.

Данные мира

SavedData → load/save → world-level ownership.

Мини-чеклист перед commit

  1. Registry entry существует.
  2. Common/client логика разделена.
  3. Нужные данные сохраняются.
  4. Клиент получает нужную синхронизацию.
  5. Client → Server payloads валидируются.
  6. Assets/data JSON присутствуют.
  7. Проверен dedicated server.
  8. Mixin не заменяет уже существующий event/API.

21. Модификации vanilla через Mixin

Важно для NeoForge 1.21.1: Mixin — низкоуровневый инструмент трансформации классов. Сначала ищите обычный NeoForge event, API, registry, tag или datapack-механизм; Mixin используйте, когда доступного extension point действительно недостаточно.

Как подключается Mixin

В NeoForge 1.21.1 конфигурация Mixin указывается в src/main/resources/META-INF/neoforge.mods.toml через таблицу [[mixins]]. Сам mixin-конфиг обычно лежит в src/main/resources/. Не используйте схему с MixinTransformerConfig и ключом transformers из старого/чужого примера.

[[mixins]]
config="examplemod.mixins.json"
{
  "required": true,
  "minVersion": "0.8",
  "package": "com.examplemod.mixin",
  "compatibilityLevel": "JAVA_21",
  "mixins": [
    "EntityMixin"
  ],
  "injectors": {
    "defaultRequire": 1
  }
}

Минимальный рабочий учебный пример

Для демонстрации возьмём Entity#tick(): это проще сверить с mappings, чем придумывать сигнатуру сложного игрового callback. Внутри injection используется стандартный CallbackInfo.

@Mixin(Entity.class)
public abstract class EntityMixin {
    @Inject(method = "tick", at = @At("TAIL"))
    private void example$afterTick(CallbackInfo ci) {
        // Собственная логика после Entity#tick().
    }
}
Где файл: src/main/java/com/examplemod/mixin/EntityMixin.java. Где подключение: src/main/resources/examplemod.mixins.json + [[mixins]] в neoforge.mods.toml. Где метод: example$afterTick(...) — ваш метод, который Mixin вызывает в указанной точке.

Как выбирать @At

  • HEAD — в начале метода.
  • TAIL — в конце метода; это не «правило безопасности», а конкретная точка injection.
  • INVOKE — около вызова другого метода; требует точного target/descriptor.
  • RETURN — перед возвратом результата; для возвращаемого значения часто нужен CallbackInfoReturnable<T>.

Типовые ошибки

  • Сигнатура injection не соответствует target-методу.
  • Mixin направлен на неправильный класс или имя метода из другой версии mappings.
  • Использован remap=false без необходимости.
  • Конфигурация взята от Forge/Fabric/другой версии и не соответствует NeoForge 1.21.1.
  • Mixin пытается решить задачу, которую проще решить event/API.
Проверка версии: при переносе на новые NeoForge 1.21.x сверяйте target-класс, имя метода, descriptor и конфигурацию с mappings именно вашей версии. Например, более новые docs могут содержать дополнительные параметры [[mixins]]; это не означает, что они нужны 1.21.1.

21.2. Data Components & Component API

Для NeoForge 1.21.1: Data Components — прежде всего система данных ItemStack. Ключом является DataComponentType<T>, а значение должно быть подходящим типом данных. Для собственного компонента регистрируется собственный DataComponentType.

Использование vanilla component

ItemStack stack = new ItemStack(ModItems.RUBY.get());
stack.set(DataComponents.CUSTOM_NAME, Component.literal("Ruby"));
Component name = stack.get(DataComponents.CUSTOM_NAME);

Собственный component

public record Mana(int value) {
    public static final Codec<Mana> CODEC =
        RecordCodecBuilder.create(instance -> instance.group(
            Codec.INT.fieldOf("value").forGetter(Mana::value)
        ).apply(instance, Mana::new));
}

public static final DeferredRegister.DataComponents COMPONENTS =
    DeferredRegister.createDataComponents(Registries.DATA_COMPONENT_TYPE, MOD_ID);

public static final Supplier<DataComponentType<Mana>> MANA =
    COMPONENTS.registerComponentType(
        "mana",
        builder -> builder.persistent(Mana.CODEC)
    );

Если компонент должен передаваться по сети, добавьте подходящий networkSynchronized(StreamCodec). Значения компонентов следует рассматривать как immutable: после изменения значения записывайте новое значение через set/update.

ItemStack stack = new ItemStack(ModItems.RUBY.get());
stack.set(MANA.get(), new Mana(100));
Mana mana = stack.getOrDefault(MANA.get(), new Mana(0));
Не путать: Component из текста Minecraft — это text component, например Component.literal(...). DataComponentType<T> — тип ключа data component. AttachmentType<T> — отдельная система NeoForge для attachments.

В 1.21.1 не следует писать несуществующий DataComponents.MANA для собственного компонента и не следует объявлять AttachmentType как реализацию Data Component.

Отличие новых версий: современные NeoForge docs могут показывать дополнительные helpers и варианты работы с component holders. Для книги baseline остаётся API 1.21.1; при переходе на другую 1.21.x проверяйте сигнатуры регистратора и codec API.

21.3. World Generation

Важно: старые псевдо-классы вроде BiomeGenerator, BiomeDefinition, StructureGenerator и DecorationGenerator не являются API NeoForge 1.21.1. Не копируйте такие классы в реальный проект.

Datapack registry paths

Worldgen-данные используют data/<modid>/worldgen/... для соответствующих Minecraft datapack registries. Biome modifiers NeoForge имеют отдельный путь data/<modid>/neoforge/biome_modifier/....

Biome Modifier: добавить feature

// src/main/resources/data/examplemod/neoforge/biome_modifier/add_feature.json
{
  "type": "neoforge:add_features",
  "biomes": "#minecraft:is_overworld",
  "features": "examplemod:example_placed_feature",
  "step": "underground_ores"
}

Biome modifiers могут добавлять/удалять features и spawns и менять ряд параметров биома. Для новых мобов отдельно проверьте RegisterSpawnPlacementsEvent: одного biome modifier недостаточно для корректных spawn restrictions.

Datagen

Для data-driven worldgen NeoForge 1.21.1 использует RegistrySetBuilder и DatapackBuiltinEntriesProvider. Это принципиально отличается от выдуманного статического API вида BiomeGenerator.create(...).

public static final ResourceKey<BiomeModifier> EXAMPLE =
    ResourceKey.create(
        NeoForgeRegistries.Keys.BIOME_MODIFIERS,
        ResourceLocation.fromNamespaceAndPath(MOD_ID, "example")
    );

// В DatapackBuiltinEntriesProvider/RegistrySetBuilder:
builder.add(NeoForgeRegistries.Keys.BIOME_MODIFIERS, bootstrap -> {
    HolderGetter<Biome> biomes = bootstrap.lookup(Registries.BIOME);
    // bootstrap.register(EXAMPLE, new ...BiomeModifier(...));
});

Что с собственным биомом и структурами?

В 1.21.1 это не «зарегистрировать Java-класс BiomeDefinition». Используйте соответствующие Minecraft registry/data-driven worldgen механизмы, registry keys, codecs и datapack JSON. Конкретный пример должен соответствовать точному типу worldgen registry, поэтому в этой книге не выдаём псевдо-API за готовый код.

Правило: если путь начинается с assets/, это обычно client resources. Если речь о datapack/worldgen data, сначала проверяйте путь под data/. Для biome modifiers NeoForge namespace — data/<modid>/neoforge/biome_modifier/.
Отличие новых версий: worldgen API и набор datagen helpers меняются между 1.21.x. Если пример найден в docs 1.21.5+ или 1.21.10+, не переносите его в 1.21.1 без сверки типов, codecs и registry keys.

21.4. Дополнительные системы

Configuration

В NeoForge 1.21.1 конфигурации строятся вокруг ModConfigSpec и регистрируются через ModContainer#registerConfig. Есть типы STARTUP, CLIENT и COMMON/SERVER в зависимости от конфигурации.

Global Loot Modifiers

GLM позволяют изменять drops без копирования ванильных loot tables. В 1.21.1 используется data/neoforge/loot_modifiers/global_loot_modifiers.json плюс JSON конкретного модификатора в namespace мода.

GameTest

Для автоматической проверки игровой логики полезно выделять тестируемые сценарии: размещение блока, рецепт машины, обработку payload, spawn и т. п. Конкретный harness и annotations сверяйте с MDK 1.21.1.

SavedData

Если данные принадлежат миру/уровню, а не конкретному entity или ItemStack, рассмотрите SavedData. Это другой уровень хранения, чем Data Components и Attachments.
